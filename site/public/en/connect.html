Connecting Agents

Connect your agent: MCP, HTTP API and skill

A daemon on your Mac drives the phone and offers the same control in three forms: an MCP server for Claude Code, Codex, Claude Desktop, Cursor and other MCP clients; an HTTP API for agents and scripts (/agent/*); and a web page and native iOS app for people.

Already done by the installer

The installer registers the MCP server with Claude Code and Codex, and with Cursor and Claude Desktop when they are present (IPHONE_USE_NO_CLIENT_SETUP=1 leaves Cursor and Claude Desktop alone). It also installs the agent skill. If the phone_* tools are not loaded in a chat yet, start a new chat.

Any other MCP client

It needs only the command; on this Mac the server finds the daemon and its token by itself. Use the absolute path (replace YOU) and merge the entry into the file, keeping the servers already there.

json · mcpServers 
{
  "mcpServers": {
    "iphone-use": {
      "command": "/Users/YOU/Applications/iPhoneUse.app/Contents/MacOS/iphone-use-mcp"
    }
  }
}

Reading a result

  • The text block is compact and written for the model: the settled change after an act tool, one line per element, or a batch's verdict and end screen.
  • structuredContent is slim by default: the fields a program branches on (ok, outcome, retry_safe, error, failed_step, snapshot, …). IPHONE_USE_MCP_STRUCTURED=full sends the daemon's whole JSON, off sends none.
  • When a result cannot be confirmed, outcome: "unknown" comes with retry_safe: false. Branch on retry_safe, never on outcome: read the screen before doing anything again.

Narrow it, serve it, pick a phone

  • IPHONE_USE_MCP_TOOLS=readonly exposes only the tools that read; a comma list names exactly the tools to expose.
  • iphone-use-mcp --listen 127.0.0.1:PORT serves MCP over HTTP. A loopback listener is reachable only from the same Mac; for a client on another machine use an authenticated encrypted tunnel. A non-loopback listener requires IPHONE_USE_MCP_TOKEN and transport protection through a TLS reverse proxy or trusted encrypted tunnel; plain HTTP exposes the bearer token.
  • With several phones installed, phone_instances lists them without reconnecting, and any call can pick one with instance:"i13". Omit it to keep the configured daemon; a missing instance fails without selecting a different phone.
  • No phone at hand? iphone-use simulator start "iPhone 16 Pro", then claude mcp add iphone-sim -e IPHONE_USE_INSTANCE=sim -- iphone-use-mcp (preview, needs Xcode).

The HTTP API

HeaderWhenMeaning
Authorization: Bearer <token>every /agent/* callIPHONE_USE_AGENT_TOKEN if set; otherwise the daemon password
X-Phone-Control: 1every state-changing POSTan intent guard on top of auth, not a replacement
X-Phone-Owner: <session>control requestsclaims the phone for this session; others get 409 phone_owned while the lease is live
EndpointPurpose
GET /agent/statusReadiness and lifecycle; act only when drivable:true, otherwise report hint
GET /agent/elementsThe screen as a flattened accessibility tree with a snapshot token
GET /agent/screenshotThe screen as PNG; screens hidden from capture come back as a labelled wireframe
POST /agent/inputOne action (tap, text, scroll, launch_app, set_value…); ?return=delta also returns what changed
POST /agent/actionsUp to 24 steps validated as a whole and stopped at the first failure, with retry_safe for the batch
POST /agent/modeagent brings the runner up; human hands the phone to whoever holds it
bash 
$ AUTH="Authorization: Bearer $TOKEN"; CTL="X-Phone-Control: 1"
$ curl -s -H "$AUTH" $HOST/agent/elements                     # the screen as text + a snapshot token
$ curl -s -H "$AUTH" -H "$CTL" -X POST "$HOST/agent/input?return=delta" \
    -d '{"type":"tap","element":7,"snapshot":"…"}'            # tap, then what changed

The daemon listens on 127.0.0.1:44321 by default. Full reference: Agent API.

The skill

The installer puts the skill at ~/.agents/skills/iphone-use, with a discovery link for Claude Code. It teaches an agent this loop:

  1. Probe: phone_status; screen reads and input need drivable:true. Otherwise report the hint and stop. Reconnect once only when the task needs the phone.
  2. Look for a saved flow first: if the registry block lists one that does the task, run it with phone_flow_run.
  3. Act in batches, not taps: read the screen once, then send what you can already see how to do as one phone_run_steps batch with wait_for after each screen change.
  4. Verify each step against its postcondition; ok:true means sent, not achieved.
  5. Offer to save it as a flow, and release the phone with phone_release_owner when done.
